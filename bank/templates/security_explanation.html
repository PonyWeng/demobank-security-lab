CSRF Token：表單與伺服器兩邊都要加入

bank/security.py → token() 產生隨機 Token 存入 Session；bank/templates/dashboard.html 的正常轉帳表單加入 hidden 欄位。兩種模式的銀行表單都有 Token，切換模式改變的是後端是否驗證。

<input type="hidden" name="csrf_token" value="本次 Session 的隨機 Token">

bank/routes.py → transfer() 在修改餘額之前呼叫 verify_transfer()；Protected 會進入 bank/security.py → verify_token()，用固定時間比較檢查表單 Token 與 Session Token。B 的活動表單沒有正確 Token，因此被拒絕。

if settings()['csrf'] == 'protected':
    verify_token()  # 缺少或不符 → abort(403)

Origin：在後端檢查這個請求從哪裡來

bank/security.py → verify_transfer() 讀取瀏覽器傳來的 Origin，與 bank/endpoints.py → endpoints()['bank'] 精確比對。允許的銀行來源目前為 {{ endpoints.bank }}。B 網站的 Origin 不同，因此啟用後會被拒絕；此驗證不需要在轉帳表單新增欄位。

if settings()['origin'] and request.headers.get('Origin') != endpoints()['bank']:
    abort(403)

Cookie：防護由瀏覽器執行

bank/__init__.py 設定 HttpOnly、SameSite、Secure；bank/endpoints.py → LabSessionInterface 套用管理員選擇的 HTTPS 跨 Site Demo 策略。SameSite 的 Lax / Strict 會限制跨 Site POST Cookie，仍允許相同 Site 的跨 Origin POST。None + Secure 允許 HTTPS 跨 Site Cookie，不代表請求有正確 Token。HttpOnly 防止 JavaScript 讀取登入 Cookie，不能單獨阻止 CSRF。

用同一個 Payload 比較

  1. Vulnerable、Origin 關閉：B 的活動表單可以轉帳。
  2. Protected、Origin 關閉：同一表單缺少 Token，回傳 403。
  3. Vulnerable、Origin 開啟：同一表單來源不同，回傳 403。
  4. 到銀行使用正常轉帳表單：包含正確 Token、Origin 為銀行，仍可成功。

設定 POST /lab 本身始終驗證 Token；變更只存在你的 Session，不會改到其他同學的模式，也不會修改原始碼。
